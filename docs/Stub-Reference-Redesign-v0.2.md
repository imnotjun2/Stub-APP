# Stub 事件化重构 v0.2

## 背景

Stub 不是票据管理器，也不是一个需要用户填写大量字段的数据库。它要解决的是：用户凭一张真实票据或照片，快速留下电影、移动、入住、演出等生活事件，并在以后自然地找回当时的细节。

本轮参考三种专用产品：Flighty 的航班信息组织、Awaybook 的酒店入住模型、记录现场的演出收藏与回顾。借鉴范围是产品结构和信息优先级，不照搬它们的视觉外观；Stub 继续使用奶油纸张、暖金记忆色和票根原图的品牌语言。

## 参考拆解

| 参考产品 | 最值得借鉴 | Stub 中的对应实现 | 不照搬 |
| --- | --- | --- | --- |
| Flighty | 航班号与日期是入口，路线、时间、座位是第一屏信息；复杂字段逐层展开 | 航班模板以航班号、日期、出发/到达、时刻为主，航司和机型折叠为补充信息，并生成路线卡 | 不声称实时状态、延误预测或自动识别；没有可靠数据源时只保存用户确认的信息 |
| Awaybook | “一次入住”是核心对象；酒店搜索、入住/退房、晚数、房型和照片共同构成回忆 | 酒店模板通过地点库搜索酒店，保存地址、入住区间、房型、品牌与预订渠道，并生成入住卡 | 不把消费统计、会员权益和酒店资料库当成 MVP 核心 |
| 记录现场 | 演出具有待看/已看状态；海报、场馆、阵容、座位和日历/地图形成回顾入口 | 演出模板保存演出名、场馆、状态、阵容、座位和海报；详情首屏使用演出身份卡 | 不扩张成票务或社交平台，不让花费统计压过现场记忆 |

## 统一事件框架

每一枚 Stub 仍然只有一份 canonical record，并按以下四层组织：

1. 事件身份：模板、名称、日期。
2. 专属事实：航班路线、入住区间、演出场馆等，由模板决定。
3. 真实证据：原始票据或凭证图，始终保留且不被海报替代。
4. 个人记忆：生活照片、同行/那一刻/感受标签和一句话。

首页、旅册、存根墙与回顾只是这份记录的不同视图。旅册继续只保存排版和顺序，不复制事件内容。

## 新增流程

用户点击加号后，先选择“电影、航班、火车、酒店、演出、展览、餐饮、购物、其他”之一。界面只展示当前模板相关字段；酒店与场馆走地点搜索，电影走片名搜索，复杂补充信息默认收起。录入顺序从“选事件”开始，以“原始票据—记忆线索—生活照片—一句话”结束。

## 数据与联网边界

本地优先原则不变。MapKit 地点搜索可用于影院、酒店和场馆；电影、航班和演出资料的可靠自动补全需要正式数据源与后端密钥管理。本地 Demo 不伪装实时航班，也不把网络候选未经确认直接写入记录。
