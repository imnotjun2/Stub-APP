# Stub｜生活存根 PRD v0.2

> 产品定义：把现实生活留下的纸质凭证，变成可收藏、可检索、可回看的个人记忆档案。

| 项目 | 内容 |

## 2. 背景与机会

电影票、登机牌、火车票、演出票、小票和展览门票，既是交易凭证，也是某段生活真实发生过的证据。人们常会保留它们，却缺少一个合适的整理方式：纸张会褪色、丢失，拍进相册后又被大量照片淹没，传统票据或记账工具则更关注金额、报销和统计，无法承载“我为什么想留下它”的情绪价值。

Stub 的机会不是做一款票据管理工具，而是建立一种新的个人记录单位：每一张值得留下的纸，都是一枚“生活存根”。App 负责降低数字化成本，并把纸面信息、当时的故事和日后的回看连接起来。

## 3. 产品目标

Stub 要帮助用户完成三件事：第一，在很短时间内保存一张纸质凭证；第二，保留票面信息之外的个人语境；第三，在未来某个时刻重新遇见这段经历。

当前 HTML Demo 的首要闭环是：

**上传真实票据 → 轻量填写 → 补充标签与照片 → 保存 → 在时间轴、旅行书或存根墙中重遇。**

正式产品在这个可靠的手动闭环之上逐步加入 OCR 与内容自动补全，目标闭环为：

**扫描纸片 → 自动识别与内容建议 → 用户确认 → 进入个人存根库 → 搜索或被回忆唤起。**

### 3.1 核心价值

| 价值 | 用户感受 | 产品能力 |
|---|---|---|
| 留住 | “它不会再褪色或弄丢。” | 原图保存、裁切校正、可靠同步与导出 |
| 理清 | “我不用费劲整理。” | OCR、自动分类、日期地点识别、去重提醒 |
| 记起 | “我还能想起那一天。” | 笔记、同行人、标签、时间轴、往日回顾 |

### 3.2 非目标

MVP 不做报销、发票验真、预算管理、消费对账、公开社交、二手票务交易，也不把复杂的数据统计放在首页。这些方向会把产品从“生活记忆”拉回“财务工具”或“内容社区”。

## 4. 目标用户与核心场景

### 4.1 核心用户

核心用户是 18–35 岁、愿意保存生活凭证的人。他们可能喜欢旅行、观影、演出、展览或手账，已经在抽屉、盒子、相册或备忘录中留下票根，但整理习惯难以持续。

### 4.2 典型场景

| 场景 | 当前做法 | 主要问题 | Stub 的切入点 |
|---|---|---|---|
| 看完电影或演出 | 票根塞进包里或随手拍照 | 容易丢，照片没有上下文 | 扫描后自动识别片名、日期、场馆，补一句感受 |
| 旅行结束整理行李 | 收集登机牌、车票和景点票 | 数量多、信息分散 | 连续扫描，按旅程和时间自动聚合 |
| 清理旧抽屉 | 发现多年以前的小票 | 字迹已褪色，不记得来历 | 增强影像、手动补全，并标为“旧存根” |
| 想回忆某段生活 | 翻相册、聊天记录或纸盒 | 搜索成本高 | 按地点、时间、类型、同行人或 OCR 全文查找 |

## 5. 产品原则

1. **纸片是主角。** 首页优先呈现真实存根，而不是数据卡片和功能入口。
2. **先保存，再整理。** 用户可以只确认标题和日期，其余信息稍后补充。
3. **信息服务于记忆。** 金额、座位、商家等结构化字段用于搜索和还原现场，不主导视觉层级。
4. **保持私人感。** 默认私密，不用公开发布换取产品价值。
5. **允许不完整。** 模糊、残缺、无日期的旧票也值得被保存，产品不制造整理负担。

## 6. 信息架构

v0.2 将产品从“只有一条时间轴”扩展为四种清晰入口。上传仍是始终可触达的主操作，但首页、旅行书和存根墙必须共享同一份数据，避免用户理解为三个相互隔离的收藏夹。

| 一级入口 | 作用 | 关键内容 |
|---|---|---|
| 首页 | 按时间重新遇见生活 | 月份时间轴、快捷筛选、近期旅行、继续添加 |
| 旅行 | 把一次旅程编成一本书 | 旅行书架、路线地图、按天翻页、收录存根与照片 |
| 存根墙 | 快速浏览全部收藏 | 瀑布流总览、类型/年份/标签/旅行筛选、搜索 |
| 设置 | 管理语言、外观和数据 | 中英文切换、深浅色、同步、导出、隐私、回收站 |

“留下一张”使用全局悬浮按钮或底部导航中的突出入口，不单独占据一个内容页面。回忆功能先作为首页卡片存在；当“去年今日、随机一张、月份回顾”被验证具有持续使用价值后，再考虑独立入口。

## 7. 核心对象与数据关系

### 7.1 唯一 Stub，多种视图

每条记录统一称为“一枚存根”。一枚存根在数据层只保存一次，但可以同时出现在首页时间轴、某本旅行书和存根墙中。首页是按发生时间生成的总索引，旅行书是对同一枚存根的策展式收录，存根墙是视觉总览；三者是不同视图，不是三份内容。

这是 v0.2 的关键产品决定。若照搬纸质手帐“一张票只能贴一次”，用户会遇到重复上传、修改不同步和离开旅行书后找不到票据等问题。为了保留真实手帐感，旅行书拥有独立的页序、裁切、旋转、跨页排版和页边注，这些版式信息属于“旅行书中的摆放”，不会复制或改变存根本体。MVP 中一枚存根最多归入一本主旅行书，但仍会自动出现在首页和存根墙；用户可以选择“从首页隐藏”，其含义仅是调整展示范围，不是移动或删除数据。

| 对象 | 保存的内容 | 与 Stub 的关系 |
|---|---|---|
| Stub | 票据影像、结构化字段、故事、标签和照片 | 唯一事实来源 |
| Trip | 旅行标题、封面、日期、城市、路线和整体笔记 | 包含多枚 Stub 的策展容器 |
| TripPlacement | 所属天数、页序、版式、裁切、旋转和页边注 | 连接 Trip 与 Stub，不复制 Stub |
| ViewPreference | 首页隐藏、墙面封面选择、筛选偏好 | 仅影响展示，不改变原始内容 |

### 7.2 通用字段

| 字段 | 必填 | Demo 来源 | 正式版来源 | 说明 |
|---|---:|---|---|---|
| 原始票据影像 | 是 | 用户上传或拍摄 | 拍摄、导入、裁切增强 | 作为不可替代的原始物证保留 |
| 标题 | 是 | 用户填写 | OCR 或内容搜索建议 + 用户确认 | 如《花样年华》、MUJI 银座店、MU5237 |
| 发生日期 | 是 | 用户填写 | OCR 建议 + 用户确认 | 允许大致日期或“未知” |
| 类型 / 子类型 | 是 | 用户选择 | 自动分类 + 用户确认 | 电影、演出、旅行-机票、旅行-火车票、餐饮、展览、其他 |
| 地点 | 否 | 用户填写 | OCR、地点搜索或定位建议 | 可包含城市、场馆、机场、车站或商家 |
| 一句话 / 长笔记 | 否 | 用户输入 | 用户输入 | 一句话用于快速回看，长笔记用于完整故事 |
| 同行人 | 否 | 自由文本 | 自由文本，后续再评估联系人 | 避免首版索取联系人权限 |
| 标签 | 否 | 快捷标签 + 自定义 | 自动建议 + 用户确认 | 同时支持系统标签和个人标签 |
| 原始票面字段 | 否 | 用户填写 | OCR 建议 + 用户确认 | 金额、座位、订单号等按类型动态展示 |
| 附加照片 | 否 | 多图上传 | 多图上传、压缩与云同步 | 与票据原图分开，可用于食物、同行人、风景等现场照片 |
| 收藏时间 | 自动 | 系统 | 系统 | 用于同步与排序，不等同于发生日期 |
| 隐私与展示状态 | 自动 | 本地默认私密 | 私密默认、敏感字段遮挡、可选共享 | 包含首页隐藏等视图偏好 |

### 7.3 分类字段与标签

标签分为“结构化属性”和“个人语义标签”。IMAX、杜比影院、CINITY 等属于电影格式，应进入固定字段，便于筛选和统计；“第一次”“毕业旅行”“和妈妈”属于用户自己的标签。界面可以将两者都呈现为标签胶囊，但数据层必须区分，避免语言切换或名称修改后失去语义。

| 类型 | 结构化字段 | 推荐快捷标签 |
|---|---|---|
| 电影 | 片名、上映年份、影院、影厅、座位、放映时间、电影格式、海报 | IMAX、IMAX GT、杜比影院、CINITY、4DX、艺术电影、首映 |
| 机票 | 航司名称与代码、航班号、出发/到达机场、计划与实际时间、机型、舱等、座位、登机口 | 靠窗、红眼航班、转机、第一次乘坐 |
| 火车票 | 车次、出发/到达车站、发车时间、车型或列车类型、席别、车厢、座位 | 高铁、动车、卧铺、靠窗、跨境列车 |
| 餐饮 | 店名、城市、日期、金额、菜品或餐别 | 早餐、咖啡、纪念日、当地味道 |
| 演出 / 展览 | 名称、场馆、日期、区域、座位、票档 | 首演、音乐节、博物馆、特展 |

电影格式、舱等、席别等结构化枚举使用稳定 ID 保存，例如 `movie_format.imax`、`flight_cabin.business`，界面再根据当前语言显示中文或英文。所有自动建议都必须允许用户覆盖；未知航司、机型和自定义影厅格式不能被系统枚举挡住。

### 7.4 影像角色

一枚存根可以有多张图片，但图片角色必须清楚。`primaryArtifact` 是真实票据或电子票截图，代表“发生过的证据”；`coverAsset` 是在首页、墙面和旅行书封面中优先展示的海报或照片；`attachments` 是食物、风景、同行人等现场照片。默认不删除或替换原始票据，用户只是在不同视图中选择更适合回看的封面。

## 8. 功能范围与自动化边界

### 8.1 P0：HTML Demo 必须形成的真实闭环

| 模块 | Demo 需求 | 验收标准 |
|---|---|---|
| 上传与拍摄 | 从相册上传真实票据；移动浏览器可调用相机；支持预览与更换 | 用户能保存自己的票据，而不是只能操作示例数据 |
| 轻量填写 | 只要求标题、日期和类型；按类型展开电影、机票或火车票字段 | 用户可以跳过所有非必填字段并保存 |
| 标签 | 提供结构化快捷标签和自定义标签 | 标签可在保存后展示、编辑，并用于筛选 |
| 多图 | 一张主票据加多张现场照片 | 食物或旅行照片与票据同时保留，角色不混淆 |
| 多视图 | 首页时间轴、旅行书架与旅行详情、存根墙、设置 | 编辑同一枚存根后，所有视图同步更新 |
| 旅行书 | 新建旅行、设置日期与路线、收录已有存根、按天查看 | 收录不复制数据；删除旅行默认不删除原始存根 |
| 本地持久化 | 刷新页面后保留存根、旅行、标签、语言与主题偏好 | 清楚提示数据只存在当前浏览器，不声称已云备份 |
| 中英文与主题 | 中文 / English 即时切换；明暗主题可切换 | 所有核心操作均有双语文案，深色模式正文和次要文字清晰可读 |

Demo 阶段可以使用少量内置影片、航司和机场数据展示“未来自动补全会是什么样”，但必须将其标记为建议或示例。未真正连接数据服务时，不能声称已经自动识别真实海报、实时航班、机型或航班状态。

当前 v0.2 Demo 的海报候选只在片名命中内置离线片库时出现；未命中时明确显示“暂无可靠候选”，允许用户直接保存票根或手动上传海报，绝不把同一张示例海报套给所有电影。航班卡内置 `MU`、`CA`、`CZ` 三个已核验识别标志并保留资源归属说明，其他航司使用二字码徽章。正式发行前仍应接入有明确授权和缓存条款的品牌数据源。

### 8.2 P1：正式 iOS MVP

| 模块 | 需求 |
|---|---|
| 扫描与导入 | 相机拍摄、相册与电子票截图导入、纸张边缘检测、旋转、裁切与质量提醒 |
| OCR 与确认 | 识别标题、日期、地点、金额及票面全文；所有识别结果进入确认页，低置信字段不静默写入 |
| 电影补全 | 用户确认片名与年份后搜索影片信息并选择海报；无匹配时保留手动封面 |
| 航班补全 | 用户输入航班号与日期后按需查询航司、机场、机型和时刻；用户确认后写入 |
| 搜索与筛选 | 搜索标题、地点、标签、同行人及 OCR 全文；按类型、日期、旅行和格式筛选 |
| 数据安全 | 默认私密、设备或云端加密、删除与恢复、原图和元数据完整导出 |
| 回忆 | 去年今日、随机一张、月份与年度回顾 |

电影海报不应在仅凭 OCR 猜到相似片名后直接替换封面，因为重名、重映、语言版本和海报版本都可能造成错误。正确流程是“识别片名 → 展示候选 → 用户确认”。航班信息同理，必须以“航班号 + 日期”为最小查询条件，并在保存前明确数据来源与更新时间。航司标识缺失时使用文字或代码徽章，不抓取来源不明的 Logo；只有接入状态数据后，界面才可以显示“延误、登机中、已到达”等实时语义。

正式实现可评估 TMDB 一类有明确图片配置与路径规则的内容源；其官方文档说明海报 URL 由配置中的基础地址、尺寸和影片返回的文件路径共同组成，因此网页端应通过后端代理搜索并管理 Key，而不是把凭证暴露在前端（[TMDB Image Basics](https://developer.themoviedb.org/docs/image-basics)）。航班数据则更需要成本闸门：FlightAware 当前将 AeroAPI 定义为按查询/结果集计费的 usage-based API，并区分商业授权层级（[FlightAware AeroAPI](https://www.flightaware.com/commercial/aeroapi)），因此 Stub 应只在用户输入“航班号 + 日期”后按需查询，不做持续轮询，并把查询额度纳入付费服务成本。

### 8.3 P2：增强留存与谨慎探索

P2 可探索连续扫描、按日期地点建议组成旅行、桌面小组件、共享旅行书、情侣或家庭共同收藏、自动生成年度册、实物打印、Apple Wallet 导入和多设备协作。任何社交能力都应从“私密共享”出发，而不是公开内容流。

## 9. 核心流程

### 9.1 首次使用

首次启动用一句话说明产品价值，并直接让用户保存第一张存根。不要先要求注册、选兴趣或配置分类。完成首次保存后，再解释同步与账号价值。

### 9.2 上传与保存

1. 用户点击“留下一张”。
2. 拍摄纸片或从相册导入，并可继续添加现场照片。
3. Demo 由用户选择类型并填写核心字段；正式版先自动校正与识别，再给出内容建议。
4. 确认页突出展示影像、标题、日期和类型；电影、机票或火车票的专属字段按需展开。
5. 用户可补充“一句话”、同行人、标签和旅行归属，也可直接保存。
6. 保存后以轻量动效进入首页时间轴，并提示“已为这一天留存根”；同一记录同时进入存根墙，若已选择旅行则出现在对应书中。

### 9.3 创建和打开旅行书

1. 用户在旅行书架点击“新建旅行”，填写名称、日期、目的地并选择封面。
2. 用户可从已有存根中收录，也可在上传新票据时直接选择这次旅行。
3. 系统根据已填城市、机场、车站或坐标生成路线与地图点；缺少地点时允许用户手动补充，不能虚构位置。
4. 打开旅行后先看到地图与旅程摘要，再按“第 1 天 / 第 2 天”进入翻页式内容。
5. 用户可调整页序、封面、页边注和照片，但修改票面字段会同步回首页与存根墙。
6. 移除收录只解除旅行关联；删除旅行默认保留全部原始存根，并在确认文案中说清差异。

### 9.4 回看与搜索

首页以时间轴呈现，不把记录压缩为普通表格。存根墙负责快速扫视全部收藏，旅行书负责沉浸式回看一次旅程。用户可通过搜索词、日期、地点、类型、标签、旅行或同行人找回记录；进入详情后先看到票根影像、封面和一句话，再看到完整票面字段。

|---|---|---|
| 首页 / 存根时间轴 | 看见自己的生活并继续添加 | 真实纸片占视觉主导；年份与月份提供节奏 |
| 上传 / 扫描页 | 快速得到可读影像 | Demo 支持真实上传和拍摄；正式版的边缘检测明确，但不要做成办公扫描器 |
| 编辑确认页 | 用最少操作完成保存 | 类型字段逐步展开、自动建议可解释且容易修正、非必填内容可跳过 |
| 存根详情页 | 重温某次经历 | 影像与个人记忆优先，结构化字段次之 |
| 旅行书架 | 选择或创建一次旅行 | 每次旅行像一本有封面、日期和路线的书，不做普通文件夹列表 |
| 旅行详情 / 地图 | 理解一次旅行的范围与路线 | 地图点与存根关联；缺失地点不虚构；可进入按天翻页 |
| 旅行书页 | 沉浸式回看旅程 | 同一存根可拥有旅行专属版式和页边注，但内容修改保持全局同步 |
| 存根墙 | 快速扫视全部收藏 | 瀑布流结合电影海报、票面、航班卡和照片；筛选后仍保持视觉节奏 |
| 回忆页 | 被动重遇过去 | 每次只突出一个回忆主题，避免信息流化 |
| 搜索结果页 | 准确找回记录 | 关键词命中位置可解释，如“票面文字命中” |
| 设置页 | 管理语言、主题和数据 | 中英文与深浅色即时切换；明确本地/云端数据状态和导出入口 |

## 11. 内容语言

品牌语气应温暖、简洁、有一点诗意，但不故作伤感。产品内统一使用“存根”作为记录单位，建议词汇如下：

| 常规产品词 | Stub 建议用语 |
|---|---|
| 新建记录 | 留下一张 |
| 保存成功 | 已为这一天留存根 |
| 所有记录 | 我的存根 |
| 每日回顾 | 又见这一天 |
| 扫描失败 | 这张纸有点难认，可以重拍或手动填写 |
| 空状态 | 生活已经发生，先留下一张吧。 |

## 12. 视觉主题与中英文策略

### 12.1 深色模式

深色模式不是把浅色页面整体反相，而是建立同一套语义色彩 Token。浅色模式延续纸张、墨色和旧金色的温暖质感；深色模式使用带暖意的炭黑背景、层级清楚的深灰卡片和接近象牙白的正文。金色只承担品牌强调、选中态和少量标题，不再承担大段正文或低对比度说明文字。

| 语义角色 | 浅色方向 | 深色方向 | 约束 |
|---|---|---|---|
| 页面背景 | 暖米白纸张 | 暖炭黑 | 避免纯白与纯黑造成刺眼反差 |
| 卡片 / 书页 | 更亮的纸白 | 高于背景一级的深灰 | 边界同时依靠明度与细描边，不只靠阴影 |
| 主文字 | 墨黑 | 象牙白 | 小字号正文以 WCAG AA 4.5:1 为最低目标 |
| 次要文字 | 暖灰褐 | 明度足够的中性灰 | 不使用当前偏暗的金灰色承载关键信息 |
| 品牌强调 | 旧金色、朱红 | 提亮的金色、克制朱红 | 仅用于重点和操作状态，不用于长文 |
| 图片处理 | 保持原始影像 | 保持原始影像并加柔和边界 | 不对票据、海报或照片做全局反相 |

### 12.2 中英文

中文和英文共用同一套页面与数据，不复制两份界面。所有系统文案使用国际化 key 管理，类型、电影格式、舱等和席别等枚举使用稳定 ID 保存，再映射为 `中文 / English` 标签。用户上传的票面内容、标题、笔记和自定义标签保持原文，不做未经请求的机器翻译。

首次打开可根据浏览器或系统语言选择默认值，设置页提供明确的“中文 / English”切换并持久化。日期、月份、数字和地点排序遵循当前语言的本地化格式；品牌名始终使用 `Stub`，中文副标题为“生活存根”，英文产品描述可使用 `A keepsake for the life you lived.`。双语验收不能只检查静态首页，还要覆盖上传、类型字段、旅行书、筛选、空状态、删除确认和错误提示。

## 13. 隐私与可信度

存根可能包含姓名、行程、订单号、金额、支付信息和常去地点，因此隐私不是设置页里的附加说明，而是产品承诺。首版应做到默认私密、传输与存储加密、权限按需申请、敏感字段可隐藏、删除可恢复且最终可彻底清除。OCR 尽可能在设备端完成；若使用云端识别，必须在隐私说明中明确数据范围、保存时间和用途。

## 14. 指标与验证计划

首轮验证重点不是内容总量，而是用户能否完成闭环、愿不愿意继续保存，以及是否真的能够找回记忆。

| 目标 | 观察指标 | MVP 阶段判断方式 |
|---|---|---|
| 降低首次成本 | 首枚存根完成率、完成耗时、确认页退出率 | 先用 20–30 名目标用户建立基线，再设正式目标 |
| 建立保存习惯 | 首周保存天数、首周存根数、连续扫描使用率 | 区分“集中整理旧票”和“日常随手保存”两类行为 |
| 产生回看价值 | 搜索成功率、旧存根详情打开率、回忆入口使用率 | 访谈确认打开是否带来真实回忆，而非误触 |
| 验证多视图价值 | 首页、旅行书和墙面的访问率；同一存根跨视图打开率 | 观察三种视图是否承担不同任务，而非重复导航 |
| 验证旅行书 | 创建旅行率、收录完成率、再次打开率、地图点点击率 | 访谈确认用户是否把它理解为“一本旅程”，而非普通相册文件夹 |
| 验证丰富记录 | 标签使用率、每枚存根附加照片数、类型字段完成率 | 判断结构化字段是否帮助回忆，还是制造填写负担 |
| 保障识别可信 | 关键字段自动采纳率、手动修改率、重拍率 | 标题与日期单独统计，不能只看 OCR 总准确率 |

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 扫描步骤太重 | 用户只在清理旧物时偶尔使用 | 默认只确认三项，允许稍后整理，支持连续扫描 |
| OCR 不稳定 | 破坏信任，增加修改成本 | 显示识别置信度，低置信字段不自动假装正确 |
| 多视图被误解为多份数据 | 用户担心重复、删除或修改不同步 | 明确“收录”而非“移动”；所有视图打开同一详情；删除操作区分解除收录与删除原件 |
| 旅行书编辑过重 | 手帐感变成排版劳动 | 默认按日期与地点自动成页，版式调整保持可选 |
| 外部海报、航班与 Logo 数据不可靠或无授权 | 错误信息、成本失控或合规风险 | 使用正式 API 与许可资源；先展示候选再确认；缓存和调用额度可控；始终提供手动回退 |
| 浏览器本地数据丢失 | Demo 用户误以为已经备份 | 明示“仅保存在此浏览器”，提供导出；正式版再承诺同步和恢复 |
| 产品过于文艺但缺乏实用性 | 新鲜感后没有持续价值 | Demo 先验证搜索与多视图回看；正式版持续投入同步、导出和识别质量 |
| 过度强调消费金额 | 变成记账或消费羞耻工具 | 金额降级为可选票面信息，默认不做消费排行榜 |
| 私密信息泄露 | 对品牌造成不可逆伤害 | 私密默认、敏感字段遮挡、明确云端处理边界 |

## 16. Demo 与正式版的能力边界

HTML Demo 的价值是验证产品逻辑和真实上传体验，不是提前假装已经拥有成熟的扫描、地图和外部数据服务。所有具有自动化观感的能力都要明确区分“本地生成的视觉表现”“候选建议”和“经过外部数据确认的事实”。

| 能力 | HTML Demo | 正式 iOS / 云服务 | 不能混淆的边界 |
|---|---|---|---|
| 票据保存 | 浏览器上传、拍摄与本地持久化 | 原生扫描、裁切增强、加密同步与恢复 | Demo 必须提示数据只在当前浏览器 |
| OCR | 手动填写为主，可展示识别入口或示例 | 设备端优先识别，必要时云端补充 | 未接模型时不显示虚假的“识别成功” |
| 电影海报 | 用户上传封面，或从明确标记的内置示例中选择 | 按片名与年份搜索正式内容源，再由用户确认 | 不凭相似片名静默套用海报，不抓取无授权图片 |
| 航班卡 | 根据手填机场、航司和航班号生成 Flighty 气质的静态卡片 | 按航班号与日期查询航司、机型、计划/实际时刻及状态 | 未接航班数据时不显示实时状态或假装准确的机型 |
| 航司标识 | 文字、二字码或已获许可的本地资产 | 授权 Logo 资产与可追溯数据来源 | Logo 缺失时优雅回退，不从搜索结果热链图片 |
| 旅行地图 | 用户选择城市或已有坐标后绘制点和路线 | 地点搜索、地理编码、离线缓存与更精确路线 | 没有坐标时请求补充，不虚构位置 |
| 多图 | 在浏览器内压缩并保存票据与现场照片 | 高清原图、云同步、空间管理 | 必须区分票据原图、封面和附加照片 |

本轮 Demo 应至少使用用户真实上传的电影票、机票或火车票走完一次完整流程，并验证以下行为：同一枚存根跨三个视图保持一致；用户能理解“收录进旅行”不会复制或移走存根；电影格式、舱等和席别等字段不会增加明显负担；切换英文和深色后仍能完成上传、编辑、筛选与删除。

## 17. 盈利模型

Stub 的盈利不应依赖广告或出售用户行程数据。最可信的模型是“免费建立收藏习惯，持续服务付费，实体纪念品增购”。免费层不建议限制本地手动存根数量，因为内容数量正是产品形成长期价值的基础；应优先限制真正带来持续成本的云空间、OCR、海报/航班查询和高级生成能力。

| 收入方式 | 可售价值 | 初步价格假设 | 优点 | 主要代价与风险 |
|---|---|---|---|---|
| 免费基础版 | 本地手动收藏、首页、基础旅行书与存根墙 | 免费 | 降低开始门槛，帮助形成长期数据资产 | 必须清楚说明无云备份；不能用内容数量惩罚核心习惯 |
| Stub+ 订阅 | 加密备份与跨设备同步、OCR 和自动补全额度、高清附件、完整导出、年度回顾、高级旅行书模板 | 建议先测试 ¥18/月、¥128/年两个锚点 | 与持续服务器、存储和 API 成本匹配；价值可不断增加 | 必须持续提供真实价值，避免“只为主题订阅”；上架 iOS 时遵循 [App Store 订阅与内购规则](https://developer.apple.com/app-store/review/guidelines/) |
| 一次性买断包 | 本地 PDF/ZIP 导出、高级主题、特定旅行书版式 | ¥12–30/包，具体由付费测试校准 | 适合不接受订阅的用户，开发和交付相对简单 | 容易碎片化权益；不应承诺长期云成本 |
| 实体纪念品 | 旅行书、年度存根册、折页、明信片或存根墙海报 | 依据打样成本测试 ¥69–199/件 | 与“把生活留下来”高度一致，付费动机自然 | 供应链、色彩还原、物流和售后复杂，需先小批量预售 |
| 品牌 / 城市联名 | 博物馆、电影节、城市活动或航旅品牌的数字纪念存根与模板 | 项目制报价 | 能获得内容与分发，且与收藏场景契合 | 商务周期长，必须保持用户数据隔离，不能让品牌内容污染私人空间 |

广告、公开内容流以及机票酒店联盟佣金不进入早期路线。它们虽然可能快速带来收入，但会把产品从“私人记忆库”推向消费推荐与流量产品，直接损害信任。若未来探索联盟服务，也只能在用户主动规划或回看旅行时提供明确、可关闭的入口，不能根据私人存根做隐蔽画像。

盈利验证按顺序执行：先确认用户会持续保存和回看，再用付费意向页测试 Stub+ 的价值组合与价格，随后邀请高意愿用户预订一版实体旅行书。订阅上线前至少要能稳定提供备份恢复或持续自动补全之一；实体打印上线前先完成少量打样、色彩校验和售后成本测算。

## 18. 分阶段路线

| 阶段 | 产品目标 | 核心交付 | 进入下一阶段的证据 |
|---|---|---|---|
| D0：数据与体验底座 | 让已有 HTML Demo 能承载扩展功能 | 唯一 Stub 模型、分类字段、标签、多图、本地迁移、明暗主题和中英文 | 已有真实存根不丢失；跨视图修改一致；双语与深色核心流程可用 |
| D1：多视图 Demo | 验证“时间轴 + 旅行书 + 墙”是否各有价值 | 四入口导航、旅行书架、地图摘要、按天书页、瀑布流墙面与筛选 | 用户能解释三个视图的差异，并能无提示完成收录、移除和查找 |
| D2：小规模验证 | 验证持续使用与付费方向 | 20–30 名目标用户测试、行为记录、访谈、数据导出和付费意向页 | 不以一次试玩为成功；至少观察首周再次保存或主动回看，并定位最有价值的付费能力 |
| N1：原生 iOS 基础版 | 把已验证闭环做成可靠 App | SwiftUI、原生扫描、本地数据库、隐私权限、Demo 数据导入、搜索与导出 | 真机长期使用稳定；用户可带走数据；核心流程不依赖云服务也成立 |
| N2：自动补全与同步 | 降低整理成本并形成持续服务价值 | OCR、电影候选、按需航班查询、地点搜索、加密同步与恢复 | 自动建议采纳率和纠错成本达到可接受水平；外部 API 成本可预测 |
| B1：商业化 | 为持续价值收费而不破坏信任 | Stub+、一次性版式包、小批量实体旅行书 | 付费来自备份、自动化或纪念品价值，不依赖广告和出售数据 |

从 HTML Demo 进入 iOS 前必须提供一次导出与导入方案，至少包含 JSON 元数据和原始图片，使当前已上传的真实票据不会成为无法迁移的孤岛。路线评审以用户任务和数据安全为门槛，而不是以页面数量为门槛。

## 19. 当前待定事项

1. iOS 是否采用 iCloud 无账号同步，还是建立独立账号体系；该选择会影响跨平台能力、成本和订阅价值。
2. 首发是否同时导入电子票截图和 PDF；建议截图进入 P0，PDF 在验证真实需求后排期。
3. 首页未知日期的旧存根如何安放；建议保留“日期待考”分组，不强迫用户填写虚假日期。
4. 一枚存根未来是否可进入多本主题收藏；v0.2 先限定一本主旅行书，待真实跨旅行需求出现后扩展。
5. 旅行书地图使用哪一种地图服务，以及地点信息在离线与跨语言场景中的表现。
6. 电影、航班和航司 Logo 的正式数据源、授权方式、缓存策略和单次调用成本。
7. 免费层与 Stub+ 的云空间、自动补全额度和实体打印权益如何组合；定价需在留存验证后测试，不以本 PRD 的假设直接上线。

## 20. 当前产品结论

Stub 最有竞争力的部分不是扫描能力本身，而是把“票据”重新定义为“生活记忆的物证”。v0.2 进一步明确：一枚存根是唯一内容单位，首页、旅行书和存根墙分别负责按时间回看、按旅程讲故事和快速浏览全部收藏。这个架构既保留数字产品的清晰与一致，也通过旅行专属排版、地图和页边注保留真正手帐的情绪。

因此当前优先级不是堆叠看似智能的功能，而是先让真实上传、结构化补充、多图记录和多视图回看形成可信闭环，再逐步把 OCR、电影海报和航班数据变成可确认、可回退的自动建议。只要“快速保存”“编成一本旅行”和“日后重遇”三个瞬间足够动人，Stub 就有机会从一次性的整理工具成长为长期的私人档案，并通过持续服务与实体纪念品建立不伤害信任的收入。
